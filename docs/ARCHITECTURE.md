# 功能应该加在哪里

这份文档帮助来自不同成员的 Agent 在同一套架构中工作。项目位于 `ember-protocol/`，下文 `game/`、`ui/`、`main.ts`、`style.css` 都位于其 `src/` 下。先读实现，文档不能代替代码；接口变化时同步更新本说明。

## 运行链路

```text
键鼠输入
  → scene.ts 收集移动、瞄准、短按动作
  → InputState
  → Simulation.tick(dt, input)
  → 战斗实体 / 状态变化 + GameEvent
      → renderer.ts 呈现世界与特效
      → audio.ts 响应音效
      → interface.ts 读取状态并展示 HUD / 菜单
```

`main.ts` 只负责组装模型、界面和 Phaser。`scene.ts` 负责引擎生命周期，不应该成为第二套战斗模型。

## 模块职责与扩展边界

| 模块                 | 可以负责                                         | 不应该负责                      |
| -------------------- | ------------------------------------------------ | ------------------------------- |
| `game/types.ts`      | 实体、输入、事件和内容 ID 类型                   | 状态副作用、实际渲染            |
| `game/config.ts`     | 枪械参数、技能说明、关卡布局与波次               | DOM 操作、运行中的实体状态      |
| `game/simulation.ts` | 伤害、弹道、敌人行为、技能、掉落、波次和状态流转 | Phaser 对象、页面元素、播放音效 |
| `game/math.ts`       | 几何、碰撞、随机函数等可独立验证逻辑             | UI 状态、隐藏的全局战斗状态     |
| `game/scene.ts`      | Phaser 场景、键鼠输入、帧更新和失焦行为          | 在输入回调中另做一份伤害结算    |
| `game/renderer.ts`   | 场景与角色绘制、粒子、可视反馈                   | 决定击杀、发放技能、改变关卡    |
| `game/audio.ts`      | 用户手势解锁、静音、合成音效                     | 音频失败时阻塞战斗              |
| `ui/interface.ts`    | 菜单、HUD、技能选择和调用模型操作                | 为了显示数值私自修改战斗规则    |
| `style.css`          | 布局、响应式界面和界面风格                       | 决定角色碰撞和世界坐标          |

目前 `Simulation` 集中拥有战斗状态，体量增长时可以抽出敌人、技能和投射物系统，但应保持唯一的状态归属。不要让多个模块各保留一份生命值、背包或敌人列表。

当前 UI 仍直接设置少量菜单及暂停状态。扩大相关功能时优先封装模型命令，再迁移调用方；不要把这种现状扩大为随意从 UI 修改实体的通道。

## 状态流转

```text
menu → combat
combat → upgrade → combat       战斗中拾取模块
combat → exit                   当前房间波次清空
exit → upgrade → exit           拾取清关模块
exit → combat                   进入下一房间，恢复初始资源
exit → won                      最终房间撤离
combat → lost                   玩家生命耗尽
won / lost → combat             重新行动
```

`paused` 是单独的暂停状态。暂停或选择技能时不得继续推进战斗。角色死亡、清关、暂停、重开和失焦是新增机制最容易遗漏的边界。

## 常见 feature 的最小落点

### 新武器

1. 在类型和枪械配置中添加唯一 ID 与参数。
2. 能用现有射击模型表达时复用该模型；特殊机制再增加对应行为。
3. 配置实际可获得的途径，支持装备、弹匣、换弹、切换与关卡恢复。
4. 添加对应枪械显示和准确说明。
5. 验证至少一种现有技能的组合，以及旧枪械仍可用。

### 新技能

1. 添加技能 ID、说明、图标，并在模型中实现真实效果。
2. 检查随机候选、已拥有技能去重、上限及重开清空。
3. 说明与伤害、穿透、控制、治疗或冲刺等已有机制的组合规则。
4. 为行为加针对性测试；不要只有文字卡片而没有效果。

### 新怪物或 Boss 招式

1. 明确可读预警、攻击窗口、移动与停止条件。
2. 更新敌人类型、数值、生成配置、行为与渲染。
3. 检查掩体寻路、近身碰撞、死亡只处理一次、掉落及清关条件。
4. 检查控制技能、爆炸、暂停和重开时的行为。

### 新关卡

优先通过 `LEVELS` 配置布局、障碍物、爆炸桶和敌人波次；保证出生点、掉落和传送门可到达。完整流程测试目前有三关、六波、43 敌人等明确断言；改变内容后要按新设计更新有效断言，不能为了变绿直接删除流程验证。

### 视觉 / HUD

表现改动只读取模型及事件；敌我子弹、拾取物、生命值和危险预警要保持可辨认。检查常用桌面窗口、较矮窗口、暂停层和技能选择层。动态文本尽量局部更新，避免每帧重建整页。

## 需要先约定的公共接口

- `WeaponId`、`SkillId`、`EnemyKind` 和实体字段。
- `InputState` 的输入语义，`GameEvent` 的类型与载荷。
- 伤害结算与技能叠加规则，掉落、敌人死亡与关卡结束的时机。
- 模型的创建、启动、暂停、选择技能、下一关和重开入口。

两个功能同时需要改变同一接口时，优先先合入兼容的接口改动，再分别实现；依赖 PR 合并前，不把相同基础提交复制到多个无关 PR。

## 验证边界

`tests/combat.test.ts` 以可注入随机源直接测试模型。当前完整流程测试用高生命夹具并安排拾取位置，只证明流程和机制能连起来，不证明平衡性、真实手感或联网同步。

当前模拟使用传入的帧间隔；**没有已经完成的固定步长网络模拟、预测、回滚或同步协议**。接入真人协作需要单独设计权威状态、输入序列、断线处理等，不能只添加房间号 UI 就宣称联网完成。

## 构建、素材和依赖

- 唯一包管理器为 npm，提交 `package.json` 和 `package-lock.json`。
- `public/` 存放静态素材；新增素材说明来源与可使用范围，不把网络链接当作稳定资源依赖。
- `dist/`、`node_modules/` 和调试日志不提交。
- Phaser 单独打包便于缓存；不要为日常功能随意调整 Vite 配置。
- 根目录 Game CI 使用 Node 22，在 Windows 与 Ubuntu 上执行同一组检查；修改操作系统相关代码要兼顾这两个环境。
